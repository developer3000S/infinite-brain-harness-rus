# Реестр репозиториев

Таблица маршрутизации harness. Одна простая запись в markdown на дочерний репозиторий, названная
`repo-registry/<slug>.md`. Ориентация корня (`CLAUDE.md` и `AGENTS.md`) читает эту папку,
чтобы решить, куда сначала идёт агент, поэтому реестр — единственное место, где harness записывает,
чем являются его дети. Файлы ориентации никогда не называют детей; записи здесь это делают.

## Правило маршрутизации, которое питает этот реестр

Агент в корне harness читает записи и ориентируется в мозг компании: запись
с `repo_kind: brain` и `brain_tier: company`. Оттуда он следует собственному
старту этого мозга. Агент, отправленный к конкретному дочернему репозиторию, идёт прямо к нему, используя его запись,
чтобы знать, в репозиторий какого вида он входит.

Норма — один мозг компании на harness. Уровень определяет ориентацию: компания первая для
межрепозиторной работы. Если корень когда-либо запускает несколько мозгов уровня компании, предложения
`primary_job` решают, к какому из них относится данная задача, но harness не оптимизирован для
такой формы.

## Когда требуется запись

Правило покрытия: каждая дочерняя директория непосредственно под `internal/` или `external/` (или под
групповой папкой external) имеет ровно одну запись здесь. Незарегистрированный дочерний репозиторий — это нарушение
политики. Запись, чья директория больше не существует, устарела; архивируйте или удалите её.
Файлы с подчёркиванием в начале (`_template.md`, `_example-company-brain.md`) не являются живыми
записями и никогда не учитываются для покрытия или маршрутизации; живая запись — это файл `<slug>.md` без
подчёркивания в начале.

Записи создаются четырёхшаговой процедурой в `ADD-A-BRAIN.md`, из `_template.md`.
Команда `register-repo` выполняет ту же процедуру.

## Поля

Каждая запись фиксирует девять полей:

| Поле | Значения | Примечания |
|---|---|---|
| repo | slug, совпадающий с именем директории | |
| path | `internal/<slug>` или `external/<slug>`, относительно harness | группировка разрешена: `external/<group>/<slug>` |
| ownership | `internal` или `external` | должно совпадать с папкой верхнего уровня в `path` |
| repo_kind | `brain`, `app` или `mixed` | чем репозиторий является по сути |
| brain_tier | `individual`, `department` или `company` | только когда `repo_kind` — `brain` или `mixed`; строка опускается для `app` |
| primary_job | одно предложение | для чего предназначен репозиторий |
| status | `active`, `supporting` или `archived` | `active` — работа ведётся; `supporting` — используется, но не управляется; `archived` — хранится только для учёта |
| remote | URL origin, или `local-only` | история резервного копирования дочернего репозитория: удалённый репозиторий, в который можно пушить, или `local-only`; для клонов стартера см. шаг 2 `ADD-A-BRAIN.md` |
| added | дата создания ��аписи | |

Про `repo_kind`: `mixed` отмечает репозиторий, который несёт реальный слой сущностей мозга вместе с
существенным кодом приложения. Сначала классифицируйте репозиторий как `brain` или `app`, и используйте `mixed`
только когда ни один из них не является честным.

Каждая запись заканчивается разделом `## Notes` для рисков, оговорок и границ. Здоровая
запись без ничего для флагов пишет одно слово "None", а не оставляет его пустым.

## Файлы здесь

- `_template.md`: шаблон записи; скопируйте его в `<slug>.md` и заполните каждое поле
- `_example-company-brain.md`: рабочий пример, клон стартера мозга, зарегистрированный как
  мозг компании вымышленной Examplecorp; не живая запись, согласно правилу покрытия
